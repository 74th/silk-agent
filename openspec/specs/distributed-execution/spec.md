# distributed-execution Specification

## Purpose
複数の共有 Worker へ会話を分散し、入力、所有権、ツール実行状態と出力を永続的に引き継ぐ。実行中の双方向制御と Sandbox の隔離を保ちながら、再起動・縮退時に二重実行や通知消失を防ぐ。

## Requirements

### Requirement: 会話所有権による分散実行
システムは、会話ごとに有効な所有者を一つ定め、所有権を持つ Worker だけに新しいエージェント入力とツール操作を許可しなければならない (SHALL)。所有権には起動を識別する値、期限、単調に増える世代を持たせなければならない (SHALL)。

#### Scenario: 同時取得
- **WHEN** 二つの Worker が同じ未割当会話を取得しようとする
- **THEN** 一方だけが有効な所有権を取得し、もう一方はその会話の SDK を起動しない

#### Scenario: 別会話の分散
- **WHEN** 複数 Worker に空きがあり、複数会話に入力が届く
- **THEN** 会話を異なる Worker に割り当てられ、それぞれ独立して進行する

### Requirement: 失効した所有者の操作を拒否する
システムは、失効した世代による新規ツール受理、会話状態更新、出力作成を拒否しなければならない (SHALL)。旧 SDK の停止を確認できない場合、新 SDK の実行を開始してはならない (SHALL NOT)。すでに受理済みのコマンドは識別子で追跡し、所有権失効だけを理由に再送・取消してはならない (SHALL NOT)。

#### Scenario: 通信断後に旧 Worker が戻る
- **WHEN** Worker A の所有権が失効し、旧世代で新しい操作を要求する
- **THEN** 操作は拒否され、新しい会話状態や出力を上書きしない

#### Scenario: 旧実行の停止を確認できない
- **WHEN** 所有権が失効したが旧 Worker の停止を確認できない
- **THEN** 会話は復旧待ちとして保持され、期限切れだけを根拠に二つ目の SDK を開始しない

#### Scenario: 旧 Worker の Pod が存在しないことを確認できた
- **WHEN** 自動回復が有効で、所有権の lease 失効から設定された待ち時間（既定は lease の2倍）が経過し、Kubernetes API が旧 incarnation の Pod UID の不在を示す
- **THEN** 旧 Worker の応答なしに所有権を解放し、証拠として Pod の不在を記録して、別の Worker へ割り当てられる

#### Scenario: Pod の状態を判断できない
- **WHEN** 自動回復が有効だが、Kubernetes API が Pod の存在を返す、またはエラーで判断できない、あるいは待ち時間が経過していない
- **THEN** 所有権は復旧待ちのまま保持され、二つ目の SDK を開始しない

#### Scenario: 一度も動き出していない割当の失効
- **WHEN** Worker が assigned から active に変えないまま所有権が失効する
- **THEN** 停止すべき SDK が存在しないため、停止の証拠なしに解放できる

### Requirement: 復旧は待機中の入力を契機とし再試行を抑制する
システムは、失効した所有権の復旧を、その会話に未処理の入力があるときに限って試みなければならない (SHALL)。失敗した復旧は指数的に間隔を延ばして再試行し、無制限に高頻度で繰り返してはならない (SHALL NOT)。復旧待ちの会話には、所有権の世代ごとに一度だけユーザへ通知しなければならない (SHALL)。

#### Scenario: 誰も待っていない会話
- **WHEN** 所有権が失効しているが、その会話に未処理の入力がない
- **THEN** 旧 Worker への停止要求や Pod の確認を行わず、入力の有無の確認だけを低頻度で行う

#### Scenario: 復旧に失敗し続ける
- **WHEN** 待機中の入力があるが、復旧が繰り返し失敗する
- **THEN** 再試行の間隔は上限まで指数的に延び、会話ごとに一定の頻度を超えない

### Requirement: 永続入力と処理状態の区別
システムは、入力の永続受付、SDK への配送開始、受理、処理完了、取消、配送不明を区別しなければならない (SHALL)。処理中の入力をメモリ上の queue だけに保持してはならない (SHALL NOT)。配送結果が不明な入力を自動再送してはならない (SHALL NOT)。

#### Scenario: SDK 送信直後の停止
- **WHEN** SDK に送った可能性のある入力の受理記録を保存する前に Worker が停止する
- **THEN** 復旧時に配送不明として扱い、未送信入力として無条件に再投入しない

#### Scenario: listener の切断
- **WHEN** 入力の変更通知が切断され、その間に追加入力が保存される
- **THEN** 再接続後に未処理入力を読み直し、通知欠落で入力を失わない

### Requirement: 実行と入出力配送の独立
システムは、turn、ツール、入力ガード、Slack 出力の完了待ちで、その会話の停止受付を塞いではならない (SHALL NOT)。SDK 収容上限時も担当会話への追記・停止を受け付け、新規会話は永続的に待機させなければならない (SHALL)。

#### Scenario: Slack が送信制限中
- **WHEN** Slack 投稿が制限され、同じ会話に停止要求が届く
- **THEN** 投稿再開を待たず停止処理を進め、結果の表示を後で配送する

### Requirement: 独立した Sandbox の管理
システムは、Sandbox 管理状態を共有ストアに保存し、複数の管理プロセスから作成・再開・停止・削除を調停しなければならない (SHALL)。Worker の削除を Sandbox 削除の理由としてはならない (SHALL NOT)。実行状態が不明な Sandbox を idle として停止してはならない (SHALL NOT)。

#### Scenario: 管理サービスの再起動
- **WHEN** Sandbox 作成要求後、結果を保存する前に管理プロセスが停止する
- **THEN** 復旧時に既存リソースを識別して整合させ、同じ会話の Sandbox を重複作成しない

#### Scenario: 別プロセスのファイル操作
- **WHEN** 一つの管理プロセスが再起動し、別プロセスがファイル操作中である
- **THEN** 再起動処理は別プロセスの稼働記録を消さず、その Sandbox を停止しない

### Requirement: 運用状態の観測
システムは、割当待ち時間、稼働 SDK 数、停止処理の遅延、完了通知の遅延、所有権更新失敗、復旧待ち、配送不明、共有ストア操作量を観測可能にしなければならない (SHALL)。

#### Scenario: 容量不足
- **WHEN** 全 Worker の収容数が上限に達している
- **THEN** 新規会話は待機し、運用者は待機数と最古の待ち時間を確認できる

### Requirement: 処理済みの共有記録を保持期間の後に削除する
システムは、共有状態ストアの記録のうち、処理が終わり以後の判断に使わないものを、設定した保持期間の後に自動で削除しなければならない (SHALL)。対象は、終端状態の入力と制御要求、配送済みまたは抑止した出力、終端状態で通知が済んだコマンドとその Sandbox 操作、応答済みの quiesce 要求、Slack の受信記録、heartbeat が止まった Worker の登録とする。保持期間は種類ごとに設定でき、既定は処理済みの記録が 30 日、Slack の受信記録と Worker の登録が 7 日でなければならない (SHALL)。保持期間は、記録が終端状態になった時刻（Worker は最後の heartbeat、受信記録は受信時刻）から数えなければならない (SHALL)。

処理待ち、処理中、保留（held）、未確定（uncertain）の記録と、通知が済んでいないコマンドを、保持期間によって削除してはならない (SHALL NOT)。会話ごとの管理情報（会話、所有権、Sandbox の管理情報）を、この仕組みで削除してはならない (SHALL NOT)。

#### Scenario: 完了した入力
- **WHEN** 入力が完了し、処理済みの保持期間が過ぎる
- **THEN** その入力の記録は自動で削除される

#### Scenario: 未確定の入力
- **WHEN** 入力が未確定のまま保持期間より長く経過する
- **THEN** その入力の記録は削除されず、運用者が復旧の操作で確認できる

#### Scenario: 通知が済んでいないコマンド
- **WHEN** コマンドは終了したが、完了の通知が保留されたまま保持期間が過ぎる
- **THEN** コマンドの記録は削除されない。通知が済んだ後、そこから保持期間が過ぎると削除される

#### Scenario: 再送された Slack イベント
- **WHEN** 受信記録の保持期間内に同じ Slack イベントが再送される
- **THEN** 重複として扱われ、入力は 1 件のまま

#### Scenario: 停止した Worker
- **WHEN** Worker の Pod が削除され、最後の heartbeat から Worker 登録の保持期間が過ぎる
- **THEN** その Worker の登録は削除され、稼働中の Worker の一覧に影響しない

#### Scenario: 会話の管理情報
- **WHEN** 会話が長期間使われず、その会話の入力がすべて削除される
- **THEN** 会話・所有権・Sandbox の管理情報は残り、新しい入力が来たら会話を再開できる

### Requirement: 既存の記録に保持期限を付ける
システムは、保持期限の仕組みを入れる前に終端状態になった記録に、同じ規則で保持期限を付ける運用コマンドを提供しなければならない (SHALL)。コマンドは既定では対象の件数を種類ごとに表示するだけで、書き込んではならない (SHALL NOT)。書き込みは運用者が明示的に指定したときだけ行い、すでに保持期限がある記録は変更してはならない (SHALL NOT)。何度実行しても同じ結果にならなければならない (SHALL)。

#### Scenario: 件数の確認
- **WHEN** 運用者が書き込みの指定なしでコマンドを実行する
- **THEN** 種類ごとの対象件数と除外件数（処理中・未確定など）が表示され、ストアは変更されない

#### Scenario: 保持期限の付与
- **WHEN** 運用者が書き込みを指定して実行し、続けてもう一度実行する
- **THEN** 1 回目で対象の記録に保持期限が付き、2 回目の対象件数は 0 になる

### Requirement: 保持期限の削除をインフラで有効にする
システムは、保持期限のフィールドに対するストアの自動削除の設定を、Terraform で対象のコレクションごとに管理しなければならない (SHALL)。コレクション名の接頭辞は Terraform の入力で指定でき、アプリケーションの設定と一致しなければならない (SHALL)。保持期限のフィールドは、所有権や lease の期限を表す既存のフィールドと別の名前でなければならない (SHALL)。

#### Scenario: plan を確認する
- **WHEN** 運用者が既定の接頭辞で Terraform の plan を作成する
- **THEN** 対象のコレクションごとに保持期限のフィールドの自動削除が計画され、lease の期限のフィールドは自動削除の対象にならない

### Requirement: 配置と設定の食い違いを起動時に検出する
各役割（Gateway、Worker、Control、Sandbox Service）は、起動時に、自分が動いている namespace と設定の値を照合しなければならない (SHALL)。Sandbox 管理の制御側の namespace、Sandbox Service の URL が指す namespace、Sandbox Service が受け入れる ServiceAccount の namespace が、自分の namespace と一致しない場合、その役割は起動してはならない (SHALL NOT)。起動しない場合は、食い違っている設定項目と、期待した値・実際の値をエラーとして出さなければならない (SHALL)。Kubernetes の外（ローカル開発など）で動かす場合は、照合を明示的に無効にできなければならない (SHALL)。

#### Scenario: 別のユースケースの設定で起動する
- **WHEN** ユースケース A の namespace で、ユースケース B の Sandbox Service の URL を書いた設定の Worker を起動する
- **THEN** Worker は起動せず、`sandbox_service_url` の namespace が自分の namespace と一致しないことがエラーとして出る

#### Scenario: 正しい設定で起動する
- **WHEN** ユースケース A の namespace で、A の値だけを書いた設定の役割を起動する
- **THEN** 照合は成功し、役割は通常どおり起動する

#### Scenario: ローカルで起動する
- **WHEN** 運用者が照合を無効にする指定をして、Kubernetes の外で役割を起動する
- **THEN** 照合は行われず、無効にしたことが起動時のログに出る

### Requirement: コンテナの再起動後の所有権を自動で回復する
システムは、所有権を持つ Worker の incarnation が、同じ Worker ID（同じ Pod UID）のより新しい incarnation に置き換わったことを確認できたとき、旧 incarnation のプロセスは存在しないものとして、その所有権を自動で解放しなければならない (SHALL)。Worker の予約数と SDK の稼働数は、記録された incarnation が解放する所有権の incarnation と一致するときだけ減らさなければならない (SHALL)。手動の解除でも同じである。

#### Scenario: コンテナだけが再起動した
- **WHEN** Worker の Pod は同じままコンテナが再起動し、新しい incarnation が登録され、旧 incarnation の所有権の lease が失効している
- **THEN** 旧 incarnation の停止確認の応答を待たずに、その所有権は解放され、会話は次の入力で別の（または同じ）Worker に割り当てられる

#### Scenario: 手動で解除しても新しい incarnation の予約数は変わらない
- **WHEN** 旧 incarnation の所有権を手動で解除する
- **THEN** 新しい incarnation の予約数と SDK の稼働数は変わらず、容量を超えた割り当ては起きない

### Requirement: Worker の記録がなくても所有権を解放できる
システムは、所有権の Worker の記録が保持期間（TTL）で消えていても、その所有権を自動回復と手動の解除で解放できなければならない (SHALL)。記録がないときは、予約数の更新は行わない。

#### Scenario: Worker の記録が TTL で消えた
- **WHEN** 停止した Worker の記録が削除された後に、その Worker の所有権を解放する
- **THEN** 所有権は解放され、会話は回復待ちから抜ける

### Requirement: 一つの会話の出力の滞留が他の会話の配送を止めない
システムは、Slack への出力の配送で、ある会話の出力が配送できない状態（先頭が結果不明である、再試行の待ちである）で滞留していても、他の会話の出力を、会話の数に依らず有限の時間内に配送しなければならない (SHALL)。会話内の出力の順序は守らなければならない (SHALL)。

#### Scenario: 一つの会話に出力が積み上がっている
- **WHEN** 会話 X の先頭の出力が結果不明で、X の後続の出力が配送待ち一覧の1ページを超える件数まで積み上がっている
- **THEN** 他の会話の出力は配送される

### Requirement: 投稿されていないことが確定した送信の失敗を結果不明にしない
システムは、Slack への出力の送信が失敗したとき、投稿されていないことが確定している失敗（Slack が `ok: false` で拒否した、送信前の検証に失敗した）を、結果不明として扱ってはならない (SHALL NOT)。一時的な拒否は待ちを置いて再試行し、恒久的な拒否は、その出力を失敗として確定し、以降の出力の配送を止めてはならない (SHALL NOT)。送信後に応答を失った可能性がある失敗は、従来どおり結果不明として扱い、重複した投稿を避ける。

#### Scenario: Slack が投稿を拒否した
- **WHEN** Slack が `channel_not_found` で投稿を拒否する
- **THEN** その出力は失敗として確定し、同じ会話の後続の出力は配送される

#### Scenario: 送信後に接続が切れた
- **WHEN** 送信した後に応答を受け取れず、投稿されたかどうかが分からない
- **THEN** その出力は結果不明のままとなり、再送されない

### Requirement: リセットが途中で失敗しても入力が詰まらない
システムは、リセットで会話の世代を更新した後に、リセットより後に届いた入力を新しい世代へ移す処理（再バインド）が失敗したとき、その処理を次の担当の起動時に完了させなければならない (SHALL)。旧世代の入力を、入力の検査（ガード、レート制限）の対象として繰り返し読み取ってはならない (SHALL NOT)。

#### Scenario: 再バインドの途中で Worker が停止した
- **WHEN** 世代の更新に成功した後、再バインドの途中で Worker が停止し、会話が別の Worker に割り当てられる
- **THEN** 割り当て先の Worker は、起動時に残りの入力を新しい世代へ移し、会話はリセット後の入力を順に処理する

#### Scenario: 旧世代の入力が残らない
- **WHEN** リセットが完了している
- **THEN** リセットより後に届いた入力に旧世代のものが残らず、同じ入力の検査が繰り返されない

### Requirement: コマンドの監視は Sandbox を起動しない
システムは、通知が済んでいないコマンドの状態と出力を監視で読むとき、停止中の Sandbox を再開してはならず (SHALL NOT)、失われた Sandbox の代わりに新しい Sandbox を作ってはならない (SHALL NOT)。Sandbox が失われたことが確定したコマンドは、結果不明の終端として記録し、監視の再試行を止めなければならない (SHALL)。

#### Scenario: 停止中の Sandbox
- **WHEN** idle 停止している Sandbox に、通知が済んでいないコマンドの記録がある
- **THEN** 監視は Sandbox を再開せず、idle 停止はそのまま維持される

#### Scenario: 失われた Sandbox
- **WHEN** コマンドを実行していた Sandbox が失われている（世代が変わった、または終了している）
- **THEN** そのコマンドは結果不明の終端として記録され、新しい Sandbox は作られず、監視は再試行しない

### Requirement: 分散構成の Slack の認証情報を Secret Manager から読む
システムは、分散構成の Slack の認証情報（bot token、app token）を、環境変数や k8s の Secret ではなく、ユースケースごとの Secret Manager から、Workload Identity で読まなければならない (SHALL)。Gateway は両方、Control は bot token だけを読み、Worker と Sandbox Service には読む権限を与えてはならない (SHALL NOT)。デプロイの手順は、指定の漏れによって、別の環境のトークンへ黙って切り替わってはならない (SHALL NOT)。

#### Scenario: トークンのローテーション
- **WHEN** 運用者が Secret Manager に新しいバージョンを登録し、Gateway と Control を再起動する
- **THEN** 新しいトークンで Slack に接続する

#### Scenario: 別のユースケースの認証情報
- **WHEN** あるユースケースの Worker または Control が、別のユースケースの Slack の Secret を読もうとする
- **THEN** 権限エラーになる

#### Scenario: Worker に認証情報がない
- **WHEN** Worker の Pod の環境変数とマウントを調べる
- **THEN** Slack のトークンは含まれない
