# Spec Delta

## MODIFIED Requirements

### Requirement: 1会話につきエージェントのインスタンスは1つ
システムは、同じ会話キーに対して、エージェントのセッションを同時に2つ以上作ってはならない (SHALL NOT)。ただし、旧 Worker の停止を確認できないまま自動回復を有効にした配置では、下の例外シナリオに記す残余リスクを許容する。turnの実行中に同じ会話へ入力が届いた場合は、既存のセッションへ渡さなければならない (SHALL)。

#### Scenario: 処理中の書き込み
- **WHEN** 会話`K`のturnが実行中に、会話`K`へ2通目のユーザメッセージが届く
- **THEN** 新しいエージェントのインスタンスは起動せず、2通目は実行中のセッションへ渡される

#### Scenario: 同時に届いた最初のメッセージ
- **WHEN** セッションがまだない会話`K`に、2通のユーザメッセージがほぼ同時に届く
- **THEN** 作られるセッションは1つだけで、2通とも同じセッションで処理される

#### Scenario: 旧 Worker の停止を確認できないまま Pod の不在が確認された
- **WHEN** 自動回復（`distributed.auto_recover_missing_pods`、distributed-execution の仕様）が有効で、旧 Worker の応答がなく、Kubernetes API で旧 Pod の不在が確認され、lease 失効から設定の待ち時間が経過する
- **THEN** 旧 Worker の SDK 停止の証拠なしに所有権を解放し、別の Worker が同じ会話を担当する。この例外は、分断されたノード上で強制削除後も動き続ける旧 SDK が残り得る場合に、同時に2つの SDK が動く可能性を許容するもので、無効にした配置では適用されない。状態・Outbox・Sandbox 操作は所有権の世代で拒否されるが、外部 MCP の副作用と履歴への書込みは拒否できない

#### Scenario: 異なる Worker へ同時到着
- **WHEN** 同じ会話に異なる受信プロセス経由で入力が届く
- **THEN** 有効な担当 Worker の SDK 一つに配送される

### Requirement: 同じ会話の入力は順に処理する
システムは、同じ会話への入力を、永続受付で確定した順序で1つずつ処理しなければならない (SHALL)。

停止要求は通常入力のガード完了を待たずに処理し、停止以前の未実行入力を無効にしなければならない (SHALL)。

#### Scenario: 実行中でないときの連続入力
- **WHEN** 実行中でない会話に入力`A`、`B`が順に届く
- **THEN** `A`のturnが始まった後に`B`が処理され、`B`が`A`より先に処理されることはない

#### Scenario: ガードの遅延
- **WHEN** 先行入力 A のガードが遅く、後続入力 B が届く
- **THEN** 通常入力 B は A を追い越して SDK に投入されない

### Requirement: 停止
システムは、停止要求を受け取ったとき、その会話で実行中のturnを中断し、その会話のSandboxで実行中のコマンド（バックグラウンドのコマンドを含む）を止めなければならない (SHALL)。中断後は、状態が「中断」になったことを出力イベントで返さなければならない (SHALL)。停止要求で止めたバックグラウンドのコマンドについて、終了の通知を送ってはならない (SHALL NOT)。

停止処理は入力ガード・Sandbox 準備・ツール結果待ちと独立して開始しなければならない (SHALL)。停止後の新規入力は失わず、停止完了後に処理しなければならない (SHALL)。取消が確認できないコマンドを停止成功と表示してはならない (SHALL NOT)。

#### Scenario: 実行中に停止
- **WHEN** 会話`K`でturnがツールを実行中に停止要求が届く
- **THEN** turnは中断され、実行中のコマンドは止められ、状態「中断」が返り、その会話は次の入力を受け付けられる状態になる

#### Scenario: バックグラウンドのコマンドだけが動いているときの停止
- **WHEN** 会話`K`でturnは動いていないが、バックグラウンドのコマンドが1件動いているときに停止要求が届く
- **THEN** そのコマンドは止められ、バックグラウンドのコマンドを1件停止したことが返り、終了の通知は送られない

#### Scenario: 実行中でないときの停止
- **WHEN** 実行中のturnもバックグラウンドのコマンドもない会話`K`に停止要求が届く
- **THEN** 何も中断せず、実行中の処理がないことを返す

#### Scenario: 停止境界
- **WHEN** 未実行の A、停止 S、新しい B の順に入力を受け付ける
- **THEN** A を取消し、実行中の turn とコマンドを停止し、B は停止完了後に処理する

#### Scenario: ガード待ちの停止
- **WHEN** 入力ガード処理中に許可されたユーザの停止が届く
- **THEN** ガードを待たず停止を適用し、後から戻る停止以前のガード結果を SDK に投入しない

#### Scenario: 取消結果が不明
- **WHEN** コマンド取消要求の結果を確認できない
- **THEN** 確認できない状態を知らせ、同じコマンドを再実行しない

### Requirement: システムからの通知
システムは、バックグラウンドのコマンドの終了などシステムからの通知を、会話のエージェントに届けなければならない (SHALL)。turnの実行中であればそのturnに追記し、正常な待機状態で実行中でなければ通知を入力とする新しいturnを始めなければならない (SHALL)。通知によって実行中のturnを中断してはならない (SHALL NOT)。

会話が中断状態の場合、通知だけで作業を再開してはならない (SHALL NOT)。結果を保存してチャネルへ検査済みの機械的な状態通知を送り、ユーザの再開時にエージェントへ結果を渡さなければならない (SHALL)。停止済みコマンドと旧会話世代の通知を注入してはならない (SHALL NOT)。

#### Scenario: 待機中の通知
- **WHEN** 会話`K`が正常な待機状態でturnが動いていないときに、バックグラウンドのコマンドが終了する
- **THEN** 終了の通知を入力とするturnが始まり、エージェントが結果を報告する

#### Scenario: 実行中の通知
- **WHEN** 会話`K`でturnがツールを実行中に、バックグラウンドのコマンドが終了する
- **THEN** 通知は実行中のturnに追記され、新しいturnは始まらない

#### Scenario: 担当解放後の完了
- **WHEN** 正常な idle 会話で担当 Worker が解放された後、バックグラウンドコマンドが完了する
- **THEN** 必要な Worker を割り当て、保存済み履歴で通知 turn を開始して結果を返信する

#### Scenario: 中断中の完了
- **WHEN** 中断された会話でコマンドが終了し、ユーザは再開を要求していない
- **THEN** 結果を保存し完了状態を知らせるが、エージェントの作業 turn を自動再開しない

#### Scenario: 停止と完了通知の競合
- **WHEN** 完了入力を保存した後、SDK へ渡す前に停止が確定する
- **THEN** 該当コマンドの完了入力を抑止し、通常の完了 turn を開始しない
